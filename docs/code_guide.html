1. Introduction and Architecture

Connectly is a social application written in Flutter. All data is stored on the phone in a single SQLite database (connectly_local.db), so the application works without a server. Each feature (authentication, feed, messaging, profile) is organised into the same four layers, and screens never execute SQL directly.

LayerFolderResponsibility
Presentationpresentation/Screens and widgets (layout, user input)
Applicationapplication/Controllers holding screen state (loading, errors, lists)
Domaindomain/Data models and repository interfaces
Datadata/SQLite repositories that run the SQL queries

Table 1. Layers used by every feature

1.1 Application startup

  1. main.dart starts LocalAppLoader, which opens the database, creates the demo accounts and builds the AuthController.
  2. ConnectlyApp provides the database to all screens through LocalDataScope and the signed-in user through AuthScope.
  3. AuthGate displays the Login screen when no user is signed in, or the main AppShell otherwise.
  4. AppShell contains a bottom navigation bar with four tabs: Feed, People, Chats and Profile.

1.2 How a screen obtains its data

Each screen asks LocalDataScope for a repository bound to the signed-in user's identifier. Because the identifier is given to the repository, every query is automatically limited to what that user is allowed to see.

final userId  = AuthScope.maybeOf(context)?.user?.id;
final feed    = LocalDataScope.of(context).feedFor(userId);
final chats   = LocalDataScope.of(context).messagingFor(userId);
final profile = LocalDataScope.of(context).profileFor(userId);

2. Authentication Module

The authentication module (lib/features/auth/) manages accounts, sessions, fingerprint login and password reset. It is used by the Login, Sign-up, Forgot-password and Profile screens.

2.1 Functions

  • Sign up: creates an account (name 2–80 characters, unique email, password 8–128 characters).
  • Sign in: verifies the password and creates a session valid for 7 days.
  • Restore: on start-up, reopens the saved session automatically.
  • Fingerprint login: each account may enable its own; it is selected by the email typed on the Login screen.
  • Forgot password: sends a 6-digit code by email, valid for 15 minutes.
  • Sign out: deletes the session.

2.3 Data access

Passwords are never stored in clear text, and session tokens are stored only as SHA-256 hashes. Signing in reads the user by email, checks the password in Dart, then inserts a session:

SELECT * FROM users WHERE email = ? LIMIT 1;

INSERT INTO auth_sessions (token_hash, user_id, created_at, expires_at)
VALUES (sha256(token), ?, now, now + 7 days);

The current user is found from the session token:

SELECT u.id, u.name, u.email, u.created_at
FROM users u JOIN auth_sessions s ON s.user_id = u.id
WHERE s.token_hash = ? AND s.expires_at > now;

A password reset stores a hashed code, then, if the code is correct, updates the password and removes all sessions of the account in one transaction:

UPDATE users SET password_hash = ? WHERE id = ?;
DELETE FROM auth_sessions  WHERE user_id = ?;
DELETE FROM password_resets WHERE user_id = ?;

3. Login Screen

File: lib/features/auth/presentation/login_screen.dart, with the related screens signup_screen.dart and forgot_password_screen.dart.

3.1 Functions

  • Sign in with email and password, with input validation.
  • "Remember my email" option.
  • "Sign in with fingerprint" button, shown only when the typed email has fingerprint login enabled on the phone.
  • "Forgot password?" link, "Create account" and "Continue as a guest".

3.2 Layout

The screen is a single scrollable form. From top to bottom: a welcome title ("Welcome back."), the email field, the password field with a show/hide button, the "Forgot password?" link, the "Remember my email" checkbox, an error message area, the "Sign in" button, the fingerprint button, and finally the "Create account" and "Continue as a guest" buttons. On wide screens (900 pixels or more), the welcome text is placed in a separate column on the left.

3.3 Data access

The Login screen does not access the database itself. AuthGate passes it callbacks such as onSignIn and onBiometricSignIn; these call the AuthController, which uses the authentication repository (Section 2.3). When sign-in succeeds, the controller stores the user and AuthGate replaces the Login screen with the main application.

4. Feed Screen

4.3 Data access

Loading posts

One query returns the posts together with their reaction counts, the current user's reaction and the number of comments. The WHERE clause changes with the chosen filter. Twenty-one rows are requested; if the twenty-first exists, a "Load more posts" button is shown.

SELECT p.id, p.author_id, u.name AS author_name, p.body, p.created_at,
  (SELECT kind FROM post_reactions r WHERE r.post_id = p.id AND r.user_id = :me) AS my_reaction,
  (SELECT COUNT(*) FROM post_reactions r WHERE r.post_id = p.id AND r.kind = 'like') AS likes,
  ... (same for love, celebrate, insightful) ...,
  (SELECT COUNT(*) FROM post_comments c WHERE c.post_id = p.id) AS comments
FROM posts p JOIN users u ON u.id = p.author_id
WHERE (p.author_id = :me OR followed(p.author_id) OR friend(p.author_id))
ORDER BY p.created_at DESC, p.id DESC
LIMIT 21;

Reacting

INSERT INTO post_reactions (post_id, user_id, kind) VALUES (?, :me, ?)
ON CONFLICT(post_id, user_id) DO UPDATE SET kind = excluded.kind;

People who reacted

SELECT r.user_id, u.name, r.kind
FROM post_reactions r JOIN users u ON u.id = r.user_id
WHERE r.post_id = ? ORDER BY u.name;

Comments

SELECT c.id, c.body, c.created_at, u.name AS author_name
FROM post_comments c JOIN users u ON u.id = c.author_id
WHERE c.post_id = ? ORDER BY c.created_at;

Before any action, the repository checks that the post is visible to the user. Deleting a post also deletes its reactions and comments automatically (ON DELETE CASCADE).

5. Messaging Screens

Folder: lib/features/messaging/. Messaging consists of the Chats inbox and the Conversation screen, and supports direct and group conversations with text and voice messages.

5.1 Functions

  • Inbox: search, a list of friends (tapping one opens a direct chat), and recent conversations with the last message and the number of unread messages. The list refreshes every 10 seconds.
  • Conversation: displays messages 50 at a time, sends text (1–4,000 characters), records and plays voice messages (up to 2 minutes), and shows group members. New messages are checked every 5 seconds and marked as read.
  • Unsent drafts are kept after the application is closed.

5.2 Layout

The inbox shows the title "Chats", a search field, a "Friends" section and a "Recent chats" list in which each row has an avatar, the conversation name, the last message, its time and an unread badge. The Conversation screen has an app bar with the conversation name, the list of message bubbles (own messages on the right), and an input bar at the bottom with a microphone button, a text field and a send button.

5.3 Data access

Inbox

For each conversation the user belongs to, the query finds its title (the other person's name for a direct chat), its last message and the number of unread messages, computed from the user's last_read_sequence.

SELECT c.id, c.kind, title, last.body, last.created_at,
  (SELECT COUNT(*) FROM messages m
    WHERE m.conversation_id = c.id
      AND m.sequence > mine.last_read_sequence
      AND m.sender_id <> :me) AS unread_count
FROM conversations c
JOIN conversation_members mine ON mine.conversation_id = c.id AND mine.user_id = :me
LEFT JOIN messages last ON last.sequence = (latest message of c)
ORDER BY last.created_at DESC LIMIT 100;

Messages of a conversation

SELECT m.sequence, m.sender_id, u.name, m.body, m.created_at, a.duration_ms
FROM messages m JOIN users u ON u.id = m.sender_id
LEFT JOIN message_audio a ON a.message_sequence = m.sequence
WHERE m.conversation_id = ? AND m.sequence > :lastSeen
ORDER BY m.sequence LIMIT 51;

Sending a message

Each message receives a random client_id. If sending is retried after an error, the unique constraint prevents a duplicate message.

INSERT INTO messages (conversation_id, sender_id, client_id, body, created_at)
VALUES (?, :me, ?, ?, now)
ON CONFLICT(conversation_id, sender_id, client_id) DO NOTHING;

Marking as read

UPDATE conversation_members SET last_read_sequence = ?
WHERE conversation_id = ? AND user_id = :me;

Voice messages are stored as a message with the text "Voice message"; the audio itself is stored in the message_audio table and loaded only when it is played.

6. Profile Screen

File: lib/features/auth/presentation/profile_screen.dart, using SqliteProfileRepository.

6.1 Functions

  • Edit name, email and a short biography (up to 160 characters).
  • Choose or remove a profile photo (resized to 512 × 512 pixels).
  • Set a location on the map and choose whether other accounts can see it.
  • Enable or disable fingerprint login.
  • Sign out.

6.2 Layout

A vertical list showing the profile photo with "Choose photo" and "Remove photo" buttons, the name, email and biography, and an "Edit profile" button that turns these into input fields. Below are a "Location" card, a "Fingerprint login" card and a "Sign out" button. A guest sees an invitation to sign in instead.

6.3 Data access

The profile is read with one query. LEFT JOIN is used because a new account does not yet have a profile or location row.

SELECT u.name, u.email, p.bio, p.photo, l.latitude, l.longitude, l.visible
FROM users u
LEFT JOIN user_profiles  p ON p.user_id = u.id
LEFT JOIN user_locations l ON l.user_id = u.id
WHERE u.id = :me;

Saving the details updates two tables in one transaction:

UPDATE users SET name = ?, email = ? WHERE id = :me;
INSERT INTO user_profiles (user_id, bio, updated_at) VALUES (:me, ?, now)
ON CONFLICT(user_id) DO UPDATE SET bio = excluded.bio, updated_at = excluded.updated_at;

After saving, the screen calls refreshUser() so that the new name and email appear everywhere in the application.

8. Local Cache Storage with Hive

Besides the SQLite database, the application uses Hive (package hive_flutter), a lightweight key–value store written in pure Dart. Hive keeps data in boxes; each box is a file in the application's private folder on the phone and behaves like a persistent map of keys to values. Reading from an open box is synchronous and very fast, which makes Hive suitable for small pieces of state that must be available immediately when a screen opens.

Hive is used only as a cache for user-interface state. It never holds the real application data (posts, messages, accounts), which stays in SQLite, and it never holds secrets: passwords are hashed in SQLite and session tokens are kept in secure storage (Android Keystore).

8.1 Why Hive in addition to SQLite

CriterionSQLiteHive
Data modelRelational tables with foreign keysKey–value pairs inside a box
Typical use in ConnectlyAccounts, posts, messages, profilesRemembered email, chat drafts, unsent messages
QueriesSQL (joins, filters, ordering)Direct lookup by key

8.3 Remembered login email

HiveLoginPreferences opens the box once at start-up (in LocalAppLoader) and is passed to the Login screen. When the screen opens it reads the saved email and fills the email field; after a successful sign-in it saves or deletes the value depending on the “Remember email” checkbox.

static Future<HiveLoginPreferences> open() async {
  await Hive.initFlutter();
  return HiveLoginPreferences(await Hive.openBox<String>('auth_preferences'));
}

String? get rememberedEmail => _box.get('remembered_email');

Future<void> saveEmail(String? email) async {
  if (email == null || email.isEmpty) {
    await _box.delete('remembered_email');
  } else {
    await _box.put('remembered_email', email);
  }
}

8.4 Chat drafts and pending messages

HiveChatLocalStore keeps, for each user and conversation, the text being typed and the messages that are waiting to be written. The key combines the user identifier and the conversation identifier, so two accounts on the same phone never see each other's drafts. The value is a JSON document:

{
  "draft": "See you tomorrow at",
  "outbox": [
    { "clientId": "c-1731660000", "body": "Hello!", "createdAt": "2026-11-15T10:20:00.000" }
  ]
}

The workflow is as follows:

  1. When a conversation opens, ChatController reads the record and restores the draft into the text field.
  2. While the user types, the draft is saved 250 ms after the last keystroke (a debounce), which avoids writing to disk on every character.
  3. When the user sends a message, it is first added to the outbox in Hive, then written to the messages table in SQLite. Once SQLite confirms it, the message is removed from the outbox.
  4. If the application closes before confirmation, the message reappears after restart marked “Not confirmed” with a Retry button; it is not resent automatically, to avoid duplicates.
  5. When both the draft and the outbox are empty, the key is deleted so the box does not grow.
Future<void> write(String userId, String conversationId, String encoded) async {
  final data = ChatLocalData.decode(encoded);
  if (data.draft.isEmpty && data.outbox.isEmpty) {
    await box.delete('$userId:$conversationId');
  } else {
    await box.put('$userId:$conversationId', encoded);
  }
}

8.5 Error handling and testing

Both stores are defined behind an interface (LoginPreferences, ChatLocalStore). If Hive cannot be opened, the Messages screen falls back to MemoryChatLocalStore, an in-memory implementation, so the chat remains usable and a notice is shown. The same in-memory implementation is used in the automated tests, which therefore run without writing files.

Hive data is removed together with all other data when the user clears the application's storage in Android settings. Logging out does not delete drafts; they simply load only for the account that wrote them.
